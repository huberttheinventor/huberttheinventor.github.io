REQUEST / THE FLIGHT API CHEAT SHEET

A request crosses the gap.
A controlled answer comes back.

Your app asks another system for a supported operation. The service checks the request and sends a response your app can use.

Illustrative exampleTripNote, SkyLine, flight 482, the delay, gate B12 and departure 7:40 are fictional teaching examples. The host uses the reserved .example domain. The credential is visibly fake. No live travel data is shown.

The four terms

Request

The message you send: method, address, required headers and any submitted content.

Endpoint

The address for the operation or resource you want. Here: https://api.skyline.example/flights/482.

Response

The service's HTTP status, headers and any returned content. TripNote reads the returned fields and draws its screen.

Webhook

A supported event causes the service to send a request to a callback URL you registered. The airline starts that notification.

The worked exchange

  1. TripNote's backend asks the SkyLine service for flight 482 using GET.
  2. The service checks the request and whether the caller may read that flight status.
  3. In this example it looks up the permitted flight record. Passenger names, payment details and crew schedules remain behind the service boundary.
  4. The successful response contains these JSON fields:
{
  "status": "Delayed",
  "gate": "B12",
  "departure": "7:40"
}

5. TripNote reads the labels and draws the flight screen. JSON is structured text data; HTTPS protects the transport.

GET asks for a current representation of a resource. Its intended meaning is read-only. POST submits content for the resource to process; it does not always mean creating a record.

Access and limitsA provider may use an API key, access token or another scheme. A key can identify application traffic without proving the user's identity or granting every permission. The service still checks allowed access. Keep real secrets protected on the backend. A limit of 100 requests per minute per app is this film's invented example; real quotas vary.

Read the status

CodeMeaningWhat to check
200The HTTP request succeeded.Read the documented fields. The flight can still be delayed.
404The resource was not found at that address, or its existence is concealed.Check the endpoint and identifier. This does not prove the real flight does not exist.
429Too many requests in the provider's counting period.Follow its quota and any retry guidance.

When the direction reverses

Register a callback URL and subscribe to a supported event. When that event happens, the airline sends a notification to TripNote's backend. The backend validates the sender and handles the event before updating its own screen.

Webhooks can provide near-real-time updates. Delivery can be delayed or fail; follow the provider's security and failure-handling instructions.

Keep this decision aidIdentify endpoint and method, required credential and allowed permissions, response fields and error statuses. For repeated changes, check whether the service supports a suitable webhook and how it secures and retries deliveries.
