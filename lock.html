LOCK / THE DATABASE CONCURRENCY CHEAT SHEET

Database concurrency cheat sheet: locks, atomic updates, constraints

Companion to Hubert film 16 (two people buy the last ticket, seat F12). Written 2026-10-11. SQL shown is PostgreSQL-flavoured; test on your own engine and isolation settings before relying on it.

The bug

Read, check, write is three steps. If two requests both read "available" before either writes "sold", both pass the check and both write. That is a race condition: the gap between the check and the write is the bug.

Fix 1: pessimistic locking (lock the row)

BEGIN;
SELECT status FROM seats WHERE seat = 'F12' FOR UPDATE;  -- locks the row
-- if status = 'available':
UPDATE seats SET status = 'sold' WHERE seat = 'F12';
COMMIT;                                                   -- releases the lock

A second transaction that also tries SELECT ... FOR UPDATE on that row waits until the first commits, then sees sold. Cost: waiting. Under heavy demand for one row, requests queue.

Fix 2: atomic update (remove the gap)

UPDATE seats SET status = 'sold'
WHERE seat = 'F12' AND status = 'available';

The check and the write are one statement. Read the rows-affected count: 1 means you got the seat, 0 means someone else did. Tell the second buyer it is gone.

Fix 3 (safety net): a constraint in the schema

CREATE UNIQUE INDEX one_confirmed_ticket
ON tickets (event_id, seat) WHERE status = 'confirmed';

Use a partial index like this if cancelled tickets may remain in the table; a plain UNIQUE (event_id, seat) blocks any second row for that seat. The engine refuses the second insert whatever the application does.

Which one when

ApproachStrengthCost
Row lock (FOR UPDATE)Simple to reason about, good for multi-step logicRequests wait; hot rows queue
Atomic UPDATE with conditionNo gap, no waiting beyond the row writeOnly fits checks that fit in one statement
Unique / partial unique constraintGuarantee lives in the schemaReports violation as an error you must handle

Two rules that outlive this example: keep your checks inside the write, and keep the final guarantee in the schema.

Written 2026-10-11. Example tables: seats (one row per seat) and tickets (confirmed purchases). Under REPEATABLE READ or SERIALIZABLE the lock path can fail with a serialization error instead of waiting; retry the transaction.
