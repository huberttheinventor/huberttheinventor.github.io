Your server should never carry the file.

Everyone builds the same upload service, and everyone breaks it the same way: a five gigabyte video goes to the API server, and the API server puts it in the database. It works on the first video and it is a liability by the hundredth. The fix is one idea applied four times. Your server decides who is allowed to move a file. It never touches a byte of the file itself.

The whole design, one picture. Everything after it is annotation.

Take it with you: the freight card, the four moves and what each one carries, in the order you build them.

The database is for the card, not for the cargo.

The first version everyone writes puts the file in the database, because the database is where things go. Then the backups take an hour, the restores take longer, and a query that used to be instant is crawling through somebody's holiday footage to reach a filename. Split the two. Postgres keeps the card: owner, name, size, and where it lives. The bytes go where bytes belong, which is object storage. S3, R2, GCS, all the same shape. One of them is built to hold a five gigabyte blob and hand it back cheaply, and it is not the one with the query planner in it.

Everything that passes through you, you pay for.

Splitting the storage out fixes the database and leaves the worse problem untouched: look at where the file still goes. It is still squeezed through your API server on the way past. That server now holds five gigabytes in memory or spools it to disk, for every upload, from every user, at the same time. You pay for the bandwidth in and the bandwidth out again. You pay for the memory. You pay for the bigger box you bought because of the memory. And the user waits through two trips instead of one, so you paid for a slower upload as well. Nobody decided any of this. It is just what happens when a request goes through a machine that had no reason to be in the way.

Hand back permission, not a pipe.

So stop carrying it. Before anything moves, the client asks: who am I, am I allowed, is there room. Those are the three questions only your server can answer, and answering them costs a few hundred bytes. If the answer is yes, you hand back one small signed thing. Not the file, and not a route to the file through you. Permission to put one object, in one place, and it expires. That is a pre-signed URL: a link your server signs with the storage credentials so the client can use storage directly, once, for one object, for a few minutes. The credentials never leave your server. The file never arrives at it. Storage checks the signature and takes the bytes, and you write one row saying it landed.

Twenty gigabytes will die at ninety-nine percent.

Now make it twenty gigabytes on hotel wifi and watch it fail at the end. If the upload is one object, one failure costs you all of it, and the user starts again from zero. So do not send it as one object. Cut it into parts, ten megabytes each, and send them independently. One part fails and you resend that one part. Storage glues them back together into a single object at the end. That is multipart upload, and it is the same trick as the pre-signed URL: make the expensive thing small enough that losing it does not matter. It also gives you a real progress bar and parts going up in parallel, both of which you get for free once the file stopped being one indivisible lump.

Downloads are the same four moves, backwards.

Nothing new to design. Check the row to see the file exists and that this person may have it, sign a link the same way, and let them pull from storage directly. Your server answers a question and gets out of the way, exactly as it did going up. If everyone wants the same file, do not make all of them cross an ocean for it: keep a copy near them. That is a CDN, a network of caches sitting close to your users so the second person to ask is served locally instead of from the origin. It is the fourth application of the one idea. Move the decision to your server and the bytes somewhere cheaper.

What to check in the one you already have.

Open the upload handler you shipped. If the file arrives as a request body on your server, you are paying for freight you never needed to carry, and no amount of tuning the box fixes it, because the box was never the problem. If the bytes are in a database column, the backup is the thing that will tell you first. If a large upload has no parts, someone on bad wifi is going to lose twenty gigabytes at ninety-nine percent this week and file a bug you cannot reproduce. Four questions, and you can answer all of them from one file.
