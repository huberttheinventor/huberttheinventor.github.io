PIPELINE / THE CI/CD CARD

The CI/CD card: what each half asks, and who presses the last button

CI/CD hands the steps of a release to a machine. It has two halves, and each half asks one question. CI asks: can this change safely join the main code? CD asks: can users safely get it?

The two questions

CI (continuous integration)CD (continuous delivery or deployment)
The questionCan this change safely join the main code?Can users safely get it?
What happensEvery push sets off a pipeline, a row of checks a machine runs by itself: install what the code needs, run the tests, scan for security holes, build the appThe tested code is sealed into one box (often a Docker image), put on a shelf called a registry, sent to staging (a practice copy of the live app), tested again, then sent to production
If a check failsWhen required checks are turned on, the change stays out of the main code until it is fixedA box that fails a stage is not sent to the next one

One change, step by step

  1. You push a change. The push sets off the pipeline (GitHub Actions can start a workflow on a push).
  2. CI checks run: install, tests, security scan, build.
  3. A red check on a protected branch with required checks blocks the merge. A fix is pushed and the checks run again.
  4. When the checks are green, the tested code is sealed once into one box.
  5. The box goes to a registry, then to staging, where it is tested again.
  6. Production gets that same box that was tested, not a fresh rebuild.

Delivery or deployment: who presses the last button

Continuous deliveryContinuous deployment
Last step to productionA person checks staging and presses DeployThe pipeline deploys by itself once every check is green
Martin Fowler's wording"Continuous Delivery just means that you are able to do frequent deployments but may choose not to do it""Continuous Deployment means that every change goes through the pipeline and automatically gets put into production"

The only difference is who presses the last button.

Start small: the canary release

A canary release sends the new version to a small slice of users first. Fowler and Sato describe it as "slowly rolling out the change to a small subset of users before rolling it out to the entire infrastructure", watching metrics while you do, and rolling back by rerouting users to the old version "until you have fixed the problem". If problems stay flat, the slice grows (the film shows 1, 10, 50 and 100 percent as an illustration, not a rule). If they jump, everyone goes back to the old version.

Watch for real problems too

A running app can still fail to serve people. The Kubernetes documentation says: "Sometimes, applications are temporarily unable to serve traffic." A check that only asks whether the app is up is not the same as a check that people are being served.

Why put the steps in a file

Speed helps, but the bigger win is that the steps live in a file, so every release runs the same way, in the same order, every time.

A starting sketch (GitHub Actions)

This is a minimal example of the CI half, not a complete pipeline. Save it as .github/workflows/ci.yml in a repository, and change the install and test commands to match your project (this one assumes a Node.js project).

name: ci
on: push
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

Make the checks required with a branch protection rule: "After enabling required status checks, all required status checks must pass before collaborators can merge changes" (GitHub Docs).

Remember it like this

CI asks: can this change safely join the main code? CD asks: can users safely get it?
