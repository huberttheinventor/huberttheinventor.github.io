The answer is a move.

This Doom-playing AI doesn't answer with a paragraph. It answers with the next move. The useful input is the game state, things like health, ammunition and what's nearby: structured data the program can hand to a decision, not the video pixels themselves. Here's how a game situation becomes a typed choice, and where that choice stops being the whole instruction.

The whole loop, one picture. Everything after it is annotation.

The useful input is the state, not the footage.

This AI plays Doom. Its answer isn't a paragraph, it's the next move. Pause the recording and the useful input turns out to be the game state: things like health, ammunition and what's nearby. That's information the program can pass into a decision. TypeSafe's own description of this demo is structured game-state input, not a model watching the screen.

One goal, a set of allowed moves, one precise question.

Add a goal and the moves that are actually allowed, then ask one precise question: which move fits this situation? In the recording, the instruction is: don't fire, simply dodge.

The model chooses. The program applies it.

In simplified code: read the state, ask for a decision, then let the game apply the chosen action.

state = read_game_state()
result = client.system_one(state=state, questions=questions)
move = result.answers["move"].choice
if allowed_by_rules(state, move):
    apply_action(move)
else:
    stop_or_review(move)

Simplified TypeSafe example, not the demo source; helpers not implemented or run.

The model chooses; the surrounding program does the work. read_game_state and apply_action are illustrative application helpers, and the call shape is checked against TypeSafe's own documentation, not copied from the demo.

A chosen move is not an obeyed instruction.

Back in the recording, movement and firing have separate outputs. The movement branch routes to MOVE. The trigger branch routes to TRIGGER, hold_fire. But firing continues anyway: ammo drops from 32 to 28 between 01:39 and 01:42 of the recording. Choosing a move doesn't mean the whole instruction got obeyed.

Why Jev skips the sentence.

A language model normally generates its response piece by piece, even when that response is structured data. TypeSafe built Jev to return typed decisions directly, without generating that text first.

Three question types, and TypeSafe's own number.

TypeSafe calls this a System One model. Choice selects one option. Score rates a defined scale. Noul estimates the probability of yes. Independent questions can be asked together. TypeSafe reports responses in 70 to 500 milliseconds end to end. That's the company's own published range from its 15 September 2026 launch report, vendor-reported, not a stopwatch on this recording.

A valid answer can still be the wrong move.

That's the catch: a valid answer can still be the wrong move. The program has to check the result against its own rules before acting, and decide when to stop, or hand the case to a person.

Open-Jev is not TypeSafe's model.

There's also Open-Jev: independent open-source work inspired by the idea. It isn't TypeSafe's model, and the same performance isn't promised. Keep language models for explanations. Use a decision model where the code needs a choice. The project is at zefan-cai.github.io/open-jev and github.com/Zefan-Cai/Open-Jev.
